# Glow（阁楼）

一个人的图像工作室，作为 [DeepSeek Harness](https://github.com/deepseek-ai) 插件运行。

写一句话出图、拿一张照片精修、多张图按用途合成。所有推理都走局域网里的本地模型服务，不经过任何第三方接口。

> 阁楼 = 一个人的小工作室；glow = 图像的光与质感。

## 它解决什么

给非专业的人用，所以刻意把"参数"换成了"场景"：

| 场景 | 用法 |
| --- | --- |
| **写一句话出图** | 大白话描述，模型帮你补成完整提示词 |
| **拿一张照片精修** | 9 个预设：换背景、换衣服、换发型、微调表情、换光线、去杂物、抠图纯色底、老照片修复、证件照换底色。每个预设都带"只改这里、其余尽量不动"的固定措辞 |
| **多张图合在一起** | 每张图指定用途（主体／背景／服装／色调／构图／细节），指令由系统合成 |

配套能力：

- **任务在后台跑**：切页面、刷新、最小化都不中断；任务记录落盘，进程重开还在。
- **参考图可以直接粘**：改图模式下 `Ctrl+V` 就能把剪贴板里的图贴进来，和本地选图完全同权。
- **想自己写指令也行**：改图模式有一个开关，打开后发出去的就是你写的那一整段，预设措辞、"保持不变"清单、角色句式一样都不加（开关默认关闭）。
- **看大图与对比**：全屏查看、1–5 倍缩放、与原图并排或滑动对比。
- **结果管理**：归档隐藏、按上次参数重做、最多 5 条常用提示词。

## 为什么这样设计

- **等待不在 HTTP 请求里**。生成走 Host 侧后台任务，页面只轮询进度。这既避免切页面丢结果，也避开了一个真实的坑：Node 内置 `fetch`（undici）有 300 秒响应头超时，恰好够把一次 5 分钟的精修掐断。长调用因此改走 `node:http`。
- **提交不再等于等待，排队也没有总时长上限**。服务端加了队列服务（`image-job-queue`，:9742）之后，插件只负责「提交任务 → 轮询状态 → 取回图片」，一次提交几十毫秒返回。排队、串行、任务持久化都在服务端，所以本机重启也不会丢任务：未完成的任务号写在 `~/.glow/jobs.json`，重启后接着查、接着取。任务只要还在排队或还在跑，就一直跟到服务端给出结论——**时间长短不构成放弃的理由**。
- **取消只结束等待，不结束任务**。还在排队时取消是真的取消（模型没开始）；已经开跑就停不下来，这时按取消只是「不在这儿等了」——任务照常跟到底，图跑完**照常存进作品**。花掉的那一轮算力要给回结果，不能连图一起扔掉。两种状态在界面上是两句话，不合并成一句「取消成功」。
- **连不上不算判死**。连续约三分钟读不到进度，任务变成「结果待取回」而不是失败：任务号留在记录里，可以点「继续取回」，插件重开时也会自己去问一遍。只有服务端明确说「没有这个任务」（含结果超过 7 天）才算真的没了。
- **原图在提交那一刻就留了一份**。参考图副本在提交时写进 `~/.glow/tasks/<任务 id>/`，早于任何授权失效，所以任务失败、中途关掉、甚至被放弃，原图都还在，事后仍能对比。
- **结果要自己存**。队列的结果文件只保留 7 天，插件在任务成功的同一轮就把图下载到本地画廊，不依赖那个地址长期有效。
- **只暴露真实可调的参数**。远端模型把采样步数固定为 6、guidance 固定 1.0、负向提示词直接忽略。这些做成只读展示并说明原因，而不是做成改了没用的开关。
- **参考图模式继承原图比例**，清晰度单独选档。实测精修耗时由参考图张数主导而非画布尺寸，所以提高像素几乎不增加等待。
- **"别的地方不动"靠提示词约束，不是蒙版重绘**。身份保持实测不错，但脸型仍可能轻微漂移——界面上如实写清楚，不承诺做不到的事。

## 安装

这是一个由目录安装的 DSH bundle：

1. 克隆本仓库到本地任意目录
2. 在 DSH 的 **插件** 页面用「添加插件」选择该目录（或由 `plugin_manager` 的 `install_bundle` 安装）
3. 刷新页面，左侧出现「阁楼」

## 配置

克隆后不需要改代码：点顶栏右侧的连接状态胶囊（或旁边的齿轮）打开「设置」，填两个地址即可，改完即时生效。

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 出图方式 | 后台排队 | 「后台排队」走队列服务（提交→等→取图）；「直连出图」是旧的同步方式，留作回滚 |
| 队列服务地址 | `http://127.0.0.1:9742` | `image-job-queue`，排队出图走这里 |
| 模型服务地址（回滚用） | `http://127.0.0.1:9741` | 原来的 `MiniMax-H3-Image`；切回直连时用它，也用来读尺寸上限 |
| 提示词服务地址 | `http://127.0.0.1:9739` | 写提示词用的本地模型 |
| 模型名 | `default_model` | 该服务只接受这个名字 |
| 直连出图时一次请求最多等多久 | 1800 秒 | **只约束直连出图的单次请求**。排队模式没有总时长上限：任务一直跟到服务端给出结论 |
| 图片保存目录 | 用户图片目录下的 `glow` | 留空用默认 |
| 保留参考图副本 | 开 | 开着才能事后对比原图；关掉省空间，但之后的图就对不上原图了（任务目录里的副本不受影响） |

设置存在 `~/.glow/settings.json`，**不进仓库**。也可以在插件行里用 `config` 预置同样的字段（`imageApiMode`、`imageBaseUrl`、`imageSyncBaseUrl`、`llmBaseUrl`、`llmModel`、`outputDir`、`imageTimeoutMs`、`llmTimeoutMs`、`keepReferenceCopies`），面板里的改动优先。

两种出图方式的契约：

- 后台排队（默认）：`POST /v1/images/jobs`（文生图）或 `/v1/images/jobs/edits`（编辑）提交，`GET /v1/images/jobs/{id}` 轮询，`succeeded` 后取 `result.png`。提交只花几十毫秒，长耗时全在服务端；结果文件服务端只保留 7 天，插件在成功后立刻下载并转存到本地目录。
- 直连出图（回滚）：`POST /v1/images/generations`、`/v1/images/edits` 一次等到出图，与旧版本行为一致。

唯一会主动停下排队任务的情况是**连续 45 次（约 3 分钟）读不到任务进度**——那是连接出了问题，不是任务慢，文案也这么写。

旧版本的设置（只有 `imageBaseUrl`、指向 9741）会在首次加载时自动迁移：模式改为后台排队、端口 9741 换成 9742，原地址保留为回滚地址。
