## Q1 · 扫码配对

**背景**：demo 画的是「扫码配对：地址和端口自动填好」，暗示存在一个桌面端配对页。实际没有——
DSH 插件侧栏没有该功能，为一个设置项去新增跨仓库的配对页并不划算。

**决定**（用户，2026-11-24）：

> 扫码配对 = 一段应用支持的配置文本，扫码后自动写入对应位置。
> 手机端配置页支持「把当前已填入的配置一键生成二维码并存入相册」，便于其他终端快速获取配置。

**因此 Android 侧要做三件事**：

1. **生成**：把当前设置序列化为带版本的配置串 → 渲染二维码 → 存入相册（走 `MediaStore`，
   与现有「存到相册」同一条路径）。
2. **扫码导入**：相机扫码 → 解析并校验版本与字段 → 写入设置 → 就地显示导入结果
   （成功给摘要，失败给具体原因，例如「版本太新」「缺少出图端口」）。
3. **配置串格式**：需要版本号与前缀，便于将来演进；不包含任何凭据（当前服务无鉴权）。

**依赖**：相机权限（`CAMERA`）、二维码生成库、条码扫描库。这是本批改动里**唯一新增权限**的一项。

**开放点**：二维码内容是否含模型名与超时等高级项（决定“导入后是否完全一致”）。实现时默认包含，
并提供「仅导入地址」的选项；如无异议按此执行。

## Q2 · 「自动润色描述」开关

**背景**：demo 在设置里放了一个「自动润色描述」总开关。但我们的精修/合成会在用户文本之外强制追加
结构化约束（“其余一切保持不变：面部特征、肤色、光照角度、构图…”），44 条金标准向量守的正是这部分。

**决定**（用户，2026-11-24）：

> 不提供自动扩写。沿用当前设计：必须手动点击才调用 LLM 润色，润色后的文本仍在文本框中、可继续编辑，
> 实际认定为用户输入。不论是否调用润色，都与系统约束不冲突。

**因此**：

1. **删除** demo 设置页里的「自动润色描述」开关，不新增任何自动改写路径。
2. 「帮我写」保持为手动触发的按钮，结果写回输入框（可编辑、可再改）。
3. 提交时一律“输入框当前文本 + 系统结构化约束”，两者互不影响；
   润色与否只影响前半段的措辞，不改变后半段的约束。
4. 「预览发送内容」需要**分开显示**这两段，并标明哪一段是系统追加的——否则用户会以为自己写的内容被悄悄改了。

**代价**：demo 里那句“差异可以在「预览发送内容」里看”失去意义（因为不存在自动改写）；
预览面板改为展示「你写的」+「系统会追加的」两段对照。

## Q3 · 查看器的「原图 / 结果」标签位置

**背景**：demo 让标签贴在图片左右下角。上一轮审美评审在真机上测过：灰色 50% 黑胶囊压在白照片上
只有 **3.8–4.1:1**，而且同一行两个胶囊一个落在白画面上（成灰块）、一个落在黑底上（近乎裸字），
两张图并排看时外观不一致。因此上一轮已把标签移到**照片下沿 +24dp、贴屏幕左右轨**。

**决定**（用户，2026-11-24）：**不贴图上，保持现状。**

**因此**：

1. 标签继续使用「照片下沿 +24dp、屏幕 16dp 轨、左右分列」的位置，两种分栏模式共用同一 y。
2. 不采用 demo 的贴图方案，**也不采用**“贴图上但不透明深色底”的折中——避免为了视觉再引入一次对比度博弈。
3. 该位置已通过两轮评审（标签 y 逐像素一致、对比 13.9:1），变更记录保留在
   `android-verification.md` 的审美评审台账中，不回退。

## Q4 · 「比例 × 清晰度」的像素表

**背景**：现有 7 个固定尺寸（1024² / 896×1216 / 864×1536 / 1536×864 / 1216×896 / 2048×1152 / 512²），
全部满足 MiniMax-H3 约束（边为 32 的倍数、256–2048）。改为「比例 × 清晰度」后需要一张映射表。

**决定**（用户，2026-11-24）：**三档：快速 / 推荐 / 高清，高清含 2048 档。**

| 比例 | 快速 | 推荐 | 高清 |
| --- | --- | --- | --- |
| 1:1 | 768×768 | 1024×1024 | 1536×1536 |
| 3:4 | 672×896 | 896×1216 | 1152×1536 |
| 4:3 | 896×672 | 1216×896 | 1536×1152 |
| 9:16 | 576×1024 | 864×1536 | 1152×2048 |
| 16:9 | 1024×576 | 1536×864 | 2048×1152 |

全部边为 32 的倍数且 ≤2048，符合服务端约束。

**因此**：

1. 参考图模式（精修 / 合成）的默认比例为「跟随原图」，另可选上述五种固定比例。
2. 张数仍为 1 / 2，只对文生图开放（精修与合成固定 1 张）。
3. 「小图试手 512」保留为快速档的独立入口？**不保留**——快速档已覆盖试手场景，减少一个选项。
4. 耗时预期需要向用户明示：高清档单张按历史估算会到数分钟，若队列里还有别的任务则更长。

**待实测**：2048 长边的单张耗时与成功率。这一档上线前要在真机上跑一次 2048×1152 与 1152×2048，
把实测数字写进验收记录；若服务端在该尺寸下失败率偏高，再回退到 1536 封顶。

## Q5 · 运行中的「取消」

**背景**：服务端的取消语义不是「随时能停」——`queued` 可真正取消并释放排队位；
`running` 返回 409，模型无法中断，只能本地不再等待、结果不入库。

**决定**（用户，2026-11-24）：**一个按钮，按状态给不同结果。**

**因此**：

1. 底部进度区只有一个「取消」，不随状态换文案，避免按钮跳动。
2. 按下后按当时状态落定：
   - `queued` → 真取消 → 进度区收起，提示「已取消，模型还没开始」；
   - `running` → 服务端拒绝 → 不停任务、但**结果不保存**，进度区改为「已放弃这次结果」，
     并如实说明「模型仍在跑完，但这次不保存」；
   - 取图阶段 → 直接丢弃已下载内容，同 `running` 处理。
3. 文案遵守既有约定：用户主动取消不等于失败，提示用「已取消 / 已放弃」，不用「没成功」。
4. 服务端 409 是正常答案而不是错误，实现上不能把它当异常弹错。

## Q6 · 「后台继续」

**背景**：demo 里点「后台继续」直接切到「全部作品」，进度条消失。任务仍在跑，用户需要知道它还在。

**决定**（用户，2026-11-24）：**收起进度条，只在通知栏跟踪；下次回到工作台时若任务还在，底栏自动恢复进度。**

**因此**：

1. 底栏有两种形态：**进度态**（正在生成 + 百分比 + 剩余/已用 + 后台继续 + 取消）与
   **常态**（主按钮 / 或「＋ 新建」）。
2. 点「后台继续」→ 底栏回到常态，进度只出现在系统通知里（通知已带进度文案）。
3. 任务未结束时重新进入工作台，底栏**自动**回到进度态——不需要用户再找。
4. 任务结束时底栏显示完成卡片（带缩略图 + 查看），而不是弹提示条；完成也照发系统通知。
5. 应用被杀后重开，靠已持久化的 `pending-job.json` 恢复进度态（现有机制已支持）。

## Q7 · 队列 / 同步模式开关

**背景**：demo 的设置页只暴露一个「电脑地址」，端口与模型收进高级。我们上一轮刚把队列模式设为默认、
把同步接口保留为可一键回退（`:9741`），这是服务端队列出问题时的退路。

**决定**（用户，2026-11-24）：**保留，但收进「高级」。**

**因此**：

1. 设置页主区只有：**电脑地址**（一个输入框）+ 两台服务的连接状态 + 重新测试。
2. 高级里保留：队列 / 同步模式切换、出图端口（9742）、助手端口（9739）、回退端口（9741）、
   模型名、两个超时的档位。
3. 端口从「完整 URL」改为「主机 + 端口」两个字段：主机一个、端口按用途各自一个，
   内部拼成 URL。这与 demo 的「一个地址」一致，也避免用户把 `http://` 写错。
4. 回退路径必须仍然可用：切到同步后走 `:9741`，且无需重新填地址。
5. 「队列 / 同步」属于技术选择，措辞按用户视角写（如「排队模式（推荐）/ 直连模式（旧）」），
   并在高级里留一行说明何时该切。

## Q8 · 删除的撤销

**背景**：demo 写「删除和归档都能撤销」。现在归档可移出（只改标记，成本为零），
而删除是直接删文件、不可恢复。

**决定**（用户，2026-11-24）：**不做撤销，改为删除前二次确认。**

**因此**：

1. 删除前弹确认，文案写清后果：这张图与它的描述、参考图副本会一起删掉，不可恢复。
2. 确认框里给出**缩略图或描述**，避免在长按多选时删错对象；多选删除时写明张数。
3. 归档保持即可撤销（移出归档箱），与删除的语义区分开：
   - 归档 = 收起来，可逆；
   - 删除 = 彻底移除，不逆，所以要确认。
4. 不引入回收站目录，也就没有“软删除清理任务”这类后台工作。

## 第二轮审查：影响已实现逻辑的 12 处

第一轮只处理了与 demo 明显冲突的 8 项。逐处对照代码后，又发现 12 处会改动既有行为，
逐项确认如下。

### R1 · 草稿按模式分开

**现状**：`GlowViewModel.prompt` 是一个字段，三个场景共用，切场景时文字跟着过去。

**决定**（用户，2026-11-24）：**按模式分别保存草稿。**

**因此**：`prompts: {text, refine, compose}` 三份，切场景各自恢复；`SavedStateHandle`
的三份草稿都要持久化（现在只存一个 `KEY_PROMPT`）；提交时取当前模式那一份。

### R2 · 「全部作品」独立页

**现状**：首页内联完整图库网格；归档箱是独立页面（`RootScreen.ARCHIVE`）。

**决定**（用户，2026-11-24）：**新增独立「全部作品」页，归档箱并入筛选。**

**因此**：

1. 首页只保留「以前做的」最近若干张 + 「全部 ›」入口。
2. 新页带筛选：全部 / 已归档；归档箱作为筛选结果存在，不再单独成页。
3. 归档/取消归档仍在图上操作，操作后按当前筛选决定是否还留在列表里（要给出可见反馈）。
4. 页内支持多选（见 R10）。

### R3 · 描述框的回车

**决定**（用户，2026-11-24）：**保持回车换行**，生成只能点底部按钮。

**理由**：描述常写成几行（尤其精修指令），回车即生成误触代价太大——一次误触就是几分钟排队。

**因此**：demo 的「回车直接生成」不实现；IME action 保持默认（换行）。

### R4 · 连接状态

**现状**：标题下方独立一行「服务已连接」；探测结果只有 ok/detail，不含时延。

**决定**（用户，2026-11-24）：**移到标题栏右侧胶囊（绿点 + 已连接 / 未连接），点它进设置；
不测、不显示时延。**

**因此**：

1. 正文不再为状态单独占一行，腾出的高度给内容。
2. 胶囊三态：已连接（绿）、未连接（红）、测试中（灰点 + 脉冲）。
3. 不新增 RTT 测量，`ProbeResult` 保持 `ok/detail` 两个字段——省掉一个不必要的指标，
   也避免用户拿时延数字去和 PC 上 ping 的结果对不上。
### R5 · 第 2 张参考图的默认角色

**现状**：`addRefs` 里第 1 张给 `Role.SUBJECT`，其余用传入的 `defaultRole`（默认也是主体）。

**决定**（用户，2026-11-24）：**第 2 张起默认「场景」。**

**因此**：第 1 张主体、第 2 张场景，用户仍可改。这与两类任务的常见用法一致——
精修改主体、合成把主体放进场景；也避免每张都要手动点一次角色。

### R6 · 「跟随原图」的像素计算

**现状**：`SizeFit.fit` 按参考图真实比例贴合，边吸附到 32 的倍数，按清晰度（density）决定像素预算。
这套能力上一轮刚验过（“参考图模式继承原图比例”）。

**决定**（用户，2026-11-24）：**保持真实比例精确贴合**，不把参考图吸附到五个标准比例。

**因此**：

1. 参考图模式的「跟随原图」= `SizeFit.fit(原图宽高, 所选清晰度)`，非标准比例（如 4:5）原样保留。
2. 用户选固定比例时才用 Q4 的像素表。
3. 精修/合成的默认比例为「跟随原图」，文生图默认 1:1。

### R7 · 进度预估的来源

**决定**（用户，2026-11-24）：**用服务端预估**（`progress.eta_seconds` 与 `queue_position`）。

**因此**：demo 里「预估按最近几次的耗时算」这行小字改为不承诺估算方式；客户端不维护本地耗时模型，
避免和服务端数字打架。服务端没给 eta 时只显示百分比，不编一个数字。

### R8 · 任务失败的呈现

**现状**：顶部横幅显示失败原因，主按钮在底栏。

**决定**（用户，2026-11-24）：**底部弹条 + 重试，取消顶部横幅。**

**因此**：

1. 任务相关的所有状态都收进底栏（进度态 / 完成卡片 / 常态），顶部横幅整体删除。
2. 失败 → 底栏恢复常态 + 底部弹条：原因（如“出图服务连不上”）+「重试」+ 可关闭。
3. 弹条内容与通知文案保持一致，不出现两套说法。
4. 用户主动取消不弹失败条（见 Q5）。
### R9 · 任务完成后的默认行为

**决定**（用户，2026-11-24）：**显示完成卡片（缩略图 + 查看），不自动跳转，输入内容保留。**

一句满意描述丢掉就找不回来。

### R11 · 扫码导入的写入方式

**决定**（用户，2026-11-24）：**先预览差异再确认写入。**

**因此**：

1. 扫码成功后不直接改配置，先列出「将被改动的项」：地址、端口、模式、模型、超时，逐行显示「旧值 → 新值」。
2. 值相同的不列出；只给「写入这些改动」与「取消」两个出口。
3. 写入成功后给摘要（如“已更新 4 项”），失败给具体原因（版本太新 / 字段缺失 / 格式错误）。
4. 与 Q1 的“生成侧”对称：生成时把当前配置序列化并渲染二维码存相册。
5. 配置串带版本号，解析时先校验版本再读字段；不含任何凭据。

### R13 · 不为 2048 档设预案

**背景**：Q4 定了高清含 2048×1152 / 1152×2048，我原本提出上线前实测耗时与失败率，若失败率高回退到 1536 封顶。

**决定**（用户，2026-11-24）：**不测、不设上限。**

> 不要受限于当前接入的模型服务能力，后端模型服务不行按生成报错处理就行了。

**因此**：

1. 三档按 Q4 的表如实实现，客户端不做“这档太慢所以藏起来”的降级逻辑。
2. 后端在某个尺寸上失败，就走**正常的生成失败路径**（底部弹条 + 原因 + 重试），
   不需要客户端提前排除。
3. 客户端唯一的责任是把尺寸说清楚、把失败如实转述；不替用户判断“这个尺寸大概不行”。
4. 之前的“待实测”从上线前置项里移除。
